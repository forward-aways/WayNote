# ADR-20260929：上报端点信任边界修复与加固（替代"客户端签名"方案）

- 状态：已完成（Phase 5，2026-09-29；注册保持开放，邮件验证码列后续）
- 日期：2026-09-29
- 触发：用户提出"把 client-logs 上报端点升级为签名鉴权，很重要"
- 范围：信任边界修复（XFF）、两档限流 + 全局兜底、控制字符清洗、日志文件大小上限、注册开关
- 不包含：客户端 HMAC 签名（已否决，见 §3）、Nginx 层限流（列 backlog）、多进程共享限流状态（单进程假设）

---

## 1. 背景与取证

用户诉求："上报端点升级为签名鉴权"。按流程先取证，结论：**诉求方向对（暴露面必须处理），但机制选错了，且现状比设想更严重**。

| # | 发现 | 证据（行号） | 影响 |
|---|---|---|---|
| 1 | 无条件信任 `X-Forwarded-For` | `api/v1/client_logs.py:52`、`core/middleware.py:110` | **限流按伪造 IP 分桶 → 每次换头即绕过**；访问日志 `ip` 字段同样可伪造 |
| 2 | 注册接口公开 | `api/v1/auth.py:18`（无依赖、无开关） | 域名上线即任何人可注册，占用库与资源 |
| 3 | 轮转仅时间维度 | `core/logging.py:183-184`（`when="midnight"`，无 `maxBytes`） | 被灌时单日文件无界（磁盘风险） |
| 4 | 无控制字符清洗 | `core/logging.py`（仅 `mask_text`） | `\x1b[2J` 等 ANSI 序列可污染/篡改终端显示 |
| 5 | 匿名可写 | `client_logs.py`（无鉴权依赖） | 开放式写接口（上限=被绕过的限流） |

## 2. Phase 1 分析

### 2.1 根因

**信任边界缺失**：把"来自浏览器的输入"（XFF 头、上报内容、注册请求）当作可信数据，并**在不带信任边界的数据上建立安全控制（限流）**。因此：
- 限流器在功能上存在、在安全上失效（#1）；
- 暴露面评估失真：以为"有 10 次/分钟"就没问题，实际上无上限（#1+#3）。

5 Whys：为什么可以无限写日志？→ 限流被绕过 → 因为限流 key 取自客户端可伪造的头 → 因为 IP 解析没有校验直连对端是否可信 → 因为没有定义"谁可信"（信任边界）→ **根因：缺失信任模型**。

### 2.2 这是"一类问题"

任何"基于客户端可伪造字段做安全判断"的地方都会复发：限流 key、审计日志 IP、未来风控/封禁。修复必须落在**统一的 IP 解析函数 + 全局策略配置**，而不是只改 `client_logs.py`。

## 3. 机制评估：为什么"客户端签名"不是鉴权

| 方案 | 能否确保"只有我们的应用可写" | 结论 |
|---|---|---|
| 前端内置密钥 + HMAC 签名 | **否**。SPA 的 JS 对任何访问者公开，密钥可提取；无服务端 nonce 时签名可无限重放（等同静态口令） | 否决（安全剧场，徒增复杂度） |
| 服务端签发令牌（**JWT 就是 HMAC 签名**） | 能。密钥只在服务端；令牌可过期、可绑定用户 | **采纳**（项目已有 JWT，零新依赖） |
| 匿名 + 严格限流 | 否，但把滥用成本压到可接受 | 作为兜底保留（覆盖登录页错误这一最有价值的场景） |

结论：用户要的"签名鉴权"在公开 SPA 场景下**唯一正确形态是服务端签发的 JWT**；前端自签自己的名字没有信任价值。

## 4. Phase 2 设计

### 4.1 信任边界（`app/core/net.py` 新增）

```python
def resolve_client_ip(scope: Scope, trusted_proxies: frozenset[str]) -> str:
    """直连对端可信时才采信 XFF，否则一律使用直连地址。"""
```
- 配置：`trusted_proxy_ips: str = "127.0.0.1,::1"`（逗号分隔；`middleware` 与 `client_logs` 共用同一解析）。
- 不变量：**XFF 仅在直连 peer ∈ trusted_proxies 时参与解析**；`trusted_proxies` 为空 ⇒ 永不采信 XFF。
- 反例警告（写入 `.env.example`）：把 `0.0.0.0/0` 或公网地址填入白名单 = 回到被绕过状态；只填反代所在地址（生产：Nginx 与 uvicorn 同机 → `127.0.0.1`）。
- 访问日志 `ip` 字段同步使用该函数（审计可信度一起修）。

### 4.2 两档限流 + 全局兜底（`client_logs.py` 重写限流器）

| 档次 | Key | 限额 | 说明 |
|---|---|---|---|
| 已登录（有效 JWT） | `user:{user_id}` | 20 次/分钟 | 保留完整 stack（≤4000 字符） |
| 匿名 | `anon:{ip}` | 2 次/分钟 | stack 截断至 500，覆盖登录页错误 |
| 全局 | `global` | 10 次/分钟 | 无论身份，兜底防分布式灌入 |
| 体积 | 单请求 | message ≤500 / stack 上限见上 | 既有约束保留 |

内存实现（单进程语义，文档化）；提供 `reset_rate_limit_state()` 供测试；字典超限时清空（防内存膨胀）。

### 4.3 控制字符清洗（`logging.py`）

- `sanitize_text()`：移除 C0/C1 控制字符（保留 `\n`、`\t`），在 `mask_text()` 之前应用；控制台与 JSON 两个 Formatter 统一走 `sanitize → mask`。
- 不变量：合法中文/emoji/引号不受影响；JSON 结构由 `json.dumps` 保证（本就转义）。

### 4.4 文件大小上限（`logging.py` 新 Handler）

`DailySizeRotatingFileHandler(TimedRotatingFileHandler)`：**每日轮转 OR 单文件超限，先到先转**。
- 超限轮转命名唯一：`waynote.log.2026-09-29_103012[.N]`（同日多次不覆盖）。
- 清理沿用"保留 N 份"语义：按 mtime 排序删除最旧（覆盖日期命名与超限命名两种形态）。
- 配置：`log_max_bytes: int = 10 * 1024 * 1024`（0=不限制）。
- 已知取舍：不处理 DST（中国无夏令时）；日志文件不再严格"每天恰好一个"（超限时同日多个）。

### 4.5 注册开关（`config.py` + `auth.py`）

- `allow_registration: bool = True`；关闭时 `POST /auth/register` → 403「注册已关闭」。
- 默认保持开放（不影响现有用户），**上线前由使用者显式设为 false**（个人工具的最小暴露面）。

## 5. 反例与边界

1. `trusted_proxy_ips` 配置错误（白名单过大）⇒ 回到被绕过状态；文档 + `.env.example` 警告。
2. 多进程/多 worker ⇒ 限流各自为政（当前单进程部署，明确不支持）。
3. 内存限流重启清零（可接受；Nginx 层限流列 backlog）。
4. 超限轮转在同秒内多次触发时用 `.N` 后缀，文件名排序与 mtime 排序可能不一致 → 清理统一按 mtime。
5. 清洗保留 `\n\t`：JSON 中本就转义；控制台多行输出仍可读。若未来需要防"多行伪装成多条日志"，改为替换 `\n`（当前不启用）。

## 7. 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| 前端内置密钥 HMAC 签名 | 密钥可提取、可重放；不构成鉴权（§3） |
| 直接要求全部上报必须登录 | 损失登录/注册页错误的可见性（最需要排查的场景）→ 改为两档 |
| 只改 `client_logs.py` 的 IP 取法 | 访问日志仍可伪造（同根因的第二处）→ 统一 `resolve_client_ip` |
| 依赖 Nginx 限流 | 生产可行但本地/直连无覆盖；应用层必须自带兜底 |
| 引入 slowapi/第三方限流 | 单端点需求，30 行内存令牌桶足够；避免新依赖 |

## 9. 最终结果（Phase 5）

- 状态：已完成（全量加固包；注册保持开放，邮件验证码注册列为后续路线）。
- 实际变更：
  - 新增 `core/net.py`：`resolve_client_ip`（信任边界唯一实现）+ `parse_trusted_proxies`；中间件与上报端点共用。
  - `config.py`：新增 `trusted_proxy_ips`（默认 `127.0.0.1,::1`）、`log_max_bytes`（默认 10MB）、`allow_registration`（默认 True）。
  - `logging.py`：新增 `sanitize_text`（控制字符清洗）与 `DailySizeRotatingFileHandler`（每日 OR 超限先到先转，时间戳命名、按 mtime 清理）。
  - `client_logs.py` 重写限流：登录 20/min（key=user_id）、匿名 2/min（key=真实 IP）、全局 10/min；匿名 stack 截断 500；`reset_rate_limit_state()` 供测试。
  - `auth.py`：注册开关（403「注册功能已关闭」）；`.env.example` 新增三项配置与白名单警告。
- 测试结果：
  - 后端 **26 passed**、ruff 通过（新增 6 个用例；S1 为 XFF 绕过回归，修复前必失败）。
  - 实机 9 项全过：匿名同 IP 第 3 次 429、可信代理下不同 XFF 独立分桶、登录档 3 次 204、ESC 注入被清洗且其余文本保留、tier/ip 审计字段正确。
- 偏差与经验：
  1. **实现中自查发现严重问题并修复**：若把 `sanitize_text` 放在最终输出，会连自身高亮 ANSI 一起剥掉（日志全无色）。正确做法是「先清洗原始内容，再做高亮装饰」，已加回归测试。
  2. `TimedRotatingFileHandler` 原生同日轮转会**删除同名备份**；自定义 `doRollover` 改为时间戳+序号命名，清理逻辑改为按 mtime（不再依赖父类 `extMatch`）。
  3. 用户决策：注册功能必须保留 → 开关保留但默认开放；**邮件验证码注册**列为后续独立任务（涉及邮件服务、验证码存储/过期/限频，需单独 ADR）。
  4. 生产注意：`TRUSTED_PROXY_IPS` 只填反代地址（同机部署即 127.0.0.1）；填公网段等于自毁限流。
- 遗留：Nginx 层限流（上线 backlog）；多进程部署下限流各自为政（边界，需外部限流）；邮件验证码注册（后续）。
